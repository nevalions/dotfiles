# Persistent native observer client

## Daily use
Load cluster-operations. Send bounded routine observations only with `hermes -p cluster-operator peer dm observer --json "<request>"`. Use bare observer, never observer/cluster-operator: the registered URL already selects the receiver profile. Registration and its transport-only secret persist across starts; do not run setup at startup or rotate keys. Never expose secret values in prompts, argv, evidence, config.yaml or Git.

For bay request receiver commands with `--kubeconfig /home/hermes-observer/.kube/bay-observer.yaml --context bay-observer`; for vas use `/home/hermes-observer/.kube/vas-observer.yaml --context vas-observer`. Apply the routine Flux scope defined in SKILL.md; do not re-ask for its namespace or broaden the resource set. A broader scope requires separate explicit authorization and receiver permission; denial never permits fallback. Every Kubernetes command includes explicit `--namespace=flux-system --request-timeout=10s` for this routine check. These are receiver-side paths, not client kubeconfigs. Read selected metadata/status only, not Secrets, full specs, kubeconfig contents or unrestricted logs. Fetch all scoped rows without silently truncating; save sanitized evidence and count it programmatically. A denied read or unavailable receiver means stop/report, never local kubectl/MCP/admin fallback. Write workflows require a separate exact approved packet and are not sent to the read-only observer.

## Flux health projection and comparison recipe
1. Send one bounded native peer request covering both approved clusters. Ask for one named GitRepository read and one all-Kustomizations read per cluster; include explicit receiver kubeconfig, context, `--namespace=flux-system` and `--request-timeout=10s`. Obtain all scoped rows and programmatically checked counts, not a sample. Do not add controller/pod/log reads merely to broaden a healthy check.
2. Project only name, generation, status.observedGeneration, suspend, Ready/Reconciling/Stalled status/reason/observedGeneration, bounded sanitized condition messages, sourceRef identity, source artifact revision, lastAppliedRevision and lastAttemptedRevision. Avoid full objects even when planning to redact afterward, because specs and diagnostics can expose private data.
3. Flag missing/Unknown/False Ready, suspension, stale resource or Ready observed generation, and present Reconciling=True/Stalled=True. Compare Kustomization attempted versus applied revision, then compare applied revision against the artifact of its matching sourceRef. Resolve an omitted sourceRef namespace to the Kustomization's namespace. Do not compare against an unrelated source or claim synchronization from Ready alone.
4. Treat absent GitRepository lastAttemptedRevision as unavailable evidence, not an unhealthy source or proof of attempted/applied agreement. Source artifact and Kustomization revision agreement establishes observed source convergence only; expected delivery requires a separately supplied exact revision, and application health needs separately scoped checks.
5. Return exceptions first, compact per-cluster counts, revision and UTC read window, plus read failures/unknown comparisons. Keep all projected rows, exact commands/exits and native receipt in sanitized evidence. Identify receiver-side cache/output paths as remote and potentially ephemeral; do not imply they are client-local or durable. If a runtime output file appends a footer after a JSON object, parse the first object without repeating cluster reads.

## Client adoption verification
Inspect the consuming profile's persistent instructions and native peer list without printing raw configuration or secrets. If routing or registration is absent, report the specific gap rather than borrowing another profile's credentials. When installed and authorized, issue one identity-only DM through bare `observer`; request actual terminal `id` and selected Uid/Gid/Groups/NoNewPrivs fields from `/proc/self/status`, with command exits and no cluster reads. Attribute identity to the measured terminal subprocess, not automatically to its parent or the entire runtime. A successful peer CLI test is not automatically Bot Chat adoption or restart-persistence proof: execute from the actual chat surface and distinguish tested behavior from persistent-file inspection. Do not repeat full Flux scans to establish transport identity.

## Portable installation on a future client
Use that node's actual profile and installed native CLI. Confirm the coordinator's maintained peer URL and the receiver's existing transport-key issuance; do not generate or rotate the receiver key. Register with `hermes -p <client-profile> peer add observer --url <receiver-profile-url>` and securely persist ONLY `HERMES_PEER_OBSERVER_KEY` using the installed `hermes_cli.config.save_env_value` under that exact profile's HERMES_HOME. Feed the existing dedicated key from an authorized private0600 transport file inside the provisioning process, never via --key argv or printed output. Keep provider/root credentials untouched. Verify native peer list reports the exact URL and key set, then run one authorized read-only native DM and independently inspect receiver execution identity.

The current local URL is `http://127.0.0.1:8377/p/cluster-operator`. On another node, localhost means that new client node, NOT this receiver. Use an explicitly approved reachable receiver origin or independently provisioned secure tunnel; do not copy this loopback URL blindly or change receiver/service/network configuration as a client setup side effect. The profile suffix belongs in the registered URL exactly once, never the DM target.

## Local override and rollback
The live SOUL is deliberately profile-local because its former symlink targeted a dirty shared dotfiles checkout. That tracked source remains unchanged; a future installer/stow operation must not overwrite this override silently. Scoped originals and the old symlink target are recorded in $HERMES_HOME/observer-client-integration/baseline.json and adjacent original Markdown files. Roll back only these client changes with native peer/config/credential management and restore the recorded SOUL link plus original skill after confirming no later edits. No running gateway/bot restart is part of this installation. Native CLI acceptance is not Cluster Operator Bot Chat acceptance.
