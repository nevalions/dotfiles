# Feasibility before admission and autonomous local recovery

## Standing scope
Apply to every project, incident and implementation, not only Kubernetes. This extends existing public-source and outcome-first rules; it grants no production, credential, publication or destructive authority. Use existing agents and supported board interfaces, never Hermes runtime edits.

## A short preflight inside the existing outcome card
Before releasing work, the coordinator records one compact readiness table, not a new planning card:
- Desired real-world acceptance and the next deliverable (executable candidate, not another proposal).
- Every mandatory input: exact retained path/provenance, or a specific permitted acquisition with a known source. UNKNOWN is not available. For implementation, obtain critical inputs before admission rather than merely naming a search.
- Runtime/tool/resource requirements: available and authorized now versus deferred production requirements. An offline runner can be built without claiming its production environment is validated.
- Necessary vs inherited constraints: identify which protect safety/acceptance and which are incidental properties of an old experiment.
- Intended implementer, owned workspace, independent review, remaining cumulative budget and wake subscription.

Check the whole critical input set together. Do not successively dispatch workers to rediscover one missing prerequisite per attempt. Keep this a bounded artifact/metadata inspection, not an open-ended investigation. If readiness fails, resolve the input or select a feasible alternative before release. Do not manufacture runnable placeholders or evidence.

## Missing historical evidence is not automatically a human gate
When old bytes/hash/fixture cannot be recovered, preserve historical equality as UNKNOWN. Determine whether the original user outcome actually requires exact historical reproduction. If not, Orchestrator may document a prospective controlled test using identified public inputs, same input in compared arms, and explicit limitations. This is an ordinary local method amendment within existing implementation authority, not permission for production execution or a claim about historical causality.

Do not ask the user to approve each local methodological choice, public input retrieval, offline implementation or routing hop. Ask when the choice changes user acceptance, introduces external/production effects, needs secrets/new access, creates material cost or irreversible risk, or contradicts an explicit user requirement. A new seed does not by itself prove equivalence or validity: verify compatibility, provenance and the test's inference limits before admitting implementation. Never replace real acceptance with synthetic tests.

## Budget and recurrence
Never resume an unchanged exhausted cycle. If the user has authorized workflow correction and local remediation, Orchestrator may record ONE materially redesigned local implementation cycle after the full preflight passes: changed assumption, evidence already acquired, concrete code deliverable, independently sized implementation/review limits and preserved prior consumption. This is an explicit recorded decision under existing authority, not an automatic budget refill. If that redesigned cycle hits the same prerequisite or produces no runnable candidate, stop and consolidate the actual unresolved choice; do not rename phases, add preparation cards or repeat corrections indefinitely.

## Deliverables and handoff
The next implementation must produce real files and executable local tests covering normal and failure paths. Reviewer assesses feasibility and inference validity as well as code: approving an accurate missing-input report is not implementation completion. Include the exact proposed external execution, safety bounds and rollback only after the local candidate exists; consolidate remaining production requirements into one concrete approval boundary. Preserve original incident acceptance until real application validation succeeds.

Coordinator owns this sequence after every event: inspect current card and artifacts -> classify blocker -> resolve/amend within standing authority -> verify readiness -> admit existing substantive work -> verify new run -> independent review -> external gate or actual acceptance. Never report a message, document, Ready state or offline PASS as a working incident fix.

## Scenario checks for the coordinator
1. Public dependency absent: acquire it once within public-data authority, record provenance, check other critical inputs, then implement. No operator prompt.
2. Historical fixture lost: exact reconstruction is UNKNOWN; if user acceptance does not require it, choose a compatible identified prospective fixture and document the changed inference. No production read pretending to recover history.
3. Explicit forensic reproduction requirement: no substitution; ask for a scope decision once.
4. Production credentials or deployment needed: prepare the runnable reviewed candidate locally where feasible, then request the exact scoped external action. Do not execute it.
5. Exhausted repeated preparation: no unchanged release; at most the single evidenced redesign above, never endless new allowances.
6. Seven offline tests but no runner: report incomplete implementation, not experiment readiness or incident resolution.
