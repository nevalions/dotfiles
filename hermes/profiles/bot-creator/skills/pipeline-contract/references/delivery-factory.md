# Shared Delivery factory — existing agents, one board

Load for accepted project candidates, delivery mode selection, delivery admissions and closure. Keep implementation/tests/independent native review on each existing project board. Route accepted outcomes to ONE shared `delivery` board; no per-project delivery boards, new bots, runtime code, scheduler or database. This reference extends, not replaces, contract.md, outcome-continuation.md, admission-preflight.md, workspace-lifecycle.md and delivery-and-verification-lessons.md. Preserve existing guards, models, histories and repository-required checks.

## Authority and mode boundary
“Do as recommended” for installing this workflow is NOT approval to commit, publish, merge or deploy an application. Mode choice is a requested ceiling, not authority. Verify the actual user's message or current repository policy, exact actions/exclusions, candidate binding and validity window. Obtain missing consequential approval in the canonical Orchestrator chat; retain a blocked gate and actual presentation/receipt evidence. Never infer approval from a bot, a Done source or this document.

Before OFFERING any runnable mode, inspect non-secret maintained deployment mapping and applicable repository automation: push/tag/PR events, merge triggers, GitOps watched refs, registry updates, downstream repositories and environments. UNKNOWN trigger coverage => offer only bounded discovery/preparation, not a supposedly safe executable mode. Unknown external facts cannot be resolved during an offline task: label the gate deferred. If an action can auto-deploy, gate that earliest action, not a later Cluster Operator card. Local hooks that publish/deploy also violate commit-only; don't bypass required hooks. A trigger conflicts with a mode's exclusions => withhold that mode until an approved non-deploying route is evidenced, or offer full delivery with explicit named-environment approval. Do not disable checks or automation as an implicit workaround.

| Mode | Maximum authorized action set | Required closure level | Exclusions |
|---|---|---|---|
| commit-only | local commit | local-committed | No push, PR, merge, deployment or external side effect. |
| publish-pr | local commit, approved branch push, open/update PR | pr-published | No merge; no automatic deployment without separately bound explicit scope. If trigger implies deployment, require full-delivery instead. |
| integrate | local commit, approved publication/PR and merge/integration into exact target | integrated | No deployment or auto-deploy unless explicitly scoped; if automatic deployment is inseparable, require full-delivery instead. |
| full-delivery | approved commit/publication/integration, deployment, acceptance in a named environment | environment-accepted | No other environment, unapproved rollback/cleanup, protection bypass or unrelated changes. |

Full delivery must name the exact environment, service/resources, reviewed deployment configuration, commands, rollback plan and permission, time window and original acceptance criteria. No unspecified “prod”, “default cluster” or inferred environment. A lower mode can be completed honestly while the broader user outcome remains pending; never label that production resolution.

## Repository-mandated shipping routes
Before selecting a mode, load current repository delivery instructions and bind their required entrypoint in the worker packet. A generic mode never overrides a repository shipping script. For kube-lvl47, consult the maintained repository AGENTS.md/CLAUDE.md and scripts/ship.sh (and Orchestrator's kube-lvl47-delivery skill): commit only in the retained isolated worktree; approved shipping uses scripts/ship.sh for branch publication, PR checks and protected server-side merge, not direct master push or manual bypass. Recheck current script behavior. --no-flux-wait is not PR-only and --auto-merge still requests merge. Bind approval before executing the script to its entire effect set, including bay/vas Flux reconciliation where still configured. Local commit/script preparation alone is not remote CI, integration or deployment success.

Require independently checked actual PR/head CI and final merged-SHA CI with required contexts/run receipts, plus scoped reconciliation/acceptance evidence for the requested outcome. A shipping script exit or its internal wait does not by itself replace CI Watcher verification. Missing permission means automatically present the consolidated script scope decision; never silently substitute a direct push or report full delivery complete.

## Evidence-bound cross-board handoff
Canonical non-worker Orchestrator owns reconciliation, approval presentation, small local packet preparation and supported parent management. Commiter (`commiter`), CI Watcher (`ci-watcher`) and Cluster Operator (`cluster-operator`) perform substantive preparation/verification/execution ONLY as assigned Kanban workers. Their Bot Chats may clarify scope or return a tracked handoff, never run untracked specialist jobs. Orchestrator does not replace them by executing publication, substantive CI or cluster work itself. Native workers stay pinned to their board and may not shell out to cross-board CLI/API or strip identity.

Retain a durable packet in the existing outcome artifacts (outside scratch), with:
- source board + exact source task/outcome IDs, source run/author and independent reviewer identity, accepted verdict/evidence references and timestamp;
- canonical repository + provider/remote identity (no embedded credentials), exact candidate directory/branch, base SHA, HEAD, full candidate manifest/digest covering staged/unstaged binary changes and owned untracked paths, modes/deletions/symlinks;
- complete required local tests/docs/review evidence, original outcome acceptance, applicable policy/scope/plan digests and retained failures;
- requested mode, target branch/environment/resource set, deployment-trigger evidence, exact operation packet digest, authentic approval reference/window/exclusions;
- stable job/action identity, cumulative budgets consumed/remaining, stage owner, prior intent/receipt, current state and next subscribed trigger.

Copy immutable evidence or use retained accessible artifact paths with verified hashes; never assume a Delivery worker can query the source board. Orchestrator reads the real source and exact candidate afresh, verifies independent review and evidence binding, then puts the source board/task references in Delivery BODY/artifacts as provenance. Source task IDs are NOT `--parent`/link IDs on Delivery. Installed boards prohibit cross-board edges. Only local Delivery card IDs may be dependencies; source completion cannot automatically release a cross-board dependency. A stale/missing source read, inaccessible packet or mismatch blocks handoff.

Treat branch names, paths and other literal strings as identifiers, not dependency edges: a source task token embedded in a branch name is not a claim that the task exists on the Delivery board. Preserve literal branch names. Resolve provenance with explicit source board plus task ID; actual dependency edges remain same-board only. For reference diagnostics, inspect the exact field and real source before classifying a warning as a false positive; never fabricate a local card or suppress a genuine missing dependency. Record the diagnostic qualification separately from actual completion readback.

An accepted source Done means local reviewed work, not delivery or original-outcome completion. Preserve it and the original outcome record. Orchestrator records the Delivery ID back to the outcome and final evidence back to both records via its permitted parent interface; verify each target readback. Do not reopen source implementation merely to track delivery.

## Admission and ownership
Use the retained owned candidate `--workspace dir:/absolute/candidate` for repository stages; never silently replace it with a fresh worktree or disposable scratch. Operational packet work can use its separately retained owned directory. Verify no removable workspace owner can delete the candidate. Apply whole-stage preflight and existing gate scripts; validators are structural checks, not authority.

Create only needed substantive cards, initially BLOCKED with explicit assignee, packet/body, runtime/retry settings and mode-correct completion contract. Set `--skill pipeline-contract`. Arrange canonical Orchestrator subscriptions before supported release and verify readbacks. No unassigned READY parking. Use only same-board prerequisite IDs and do not assume a Done parent proves evidence. Keep a child blocked pending fresh coordinator validation; do not pre-admit all later actions on a dependency chain that could auto-promote without a gate. Prefer just-in-time stage creation to routing-card spam.

| Stage | Sole substantive owner | Required output |
|---|---|---|
| delivery-preparation / local-commit / publish-pr / integrate | commiter | exact candidate-to-commit mapping, changed refs/PR receipt and resulting SHA; only mode-approved effects |
| ci-verification | ci-watcher | provider + exact SHA + required contexts/run IDs/status evidence, or independently verified policy-bound EXEMPT |
| deployment-preparation / deploy / environment-acceptance | cluster-operator | scoped environment/operation packet; actual deployed identity and original acceptance observations |
| coordinate / approve-present / reconcile / outcome-close | canonical non-worker orchestrator | verified source/candidate/authority, exact next action or visible gate, closure level |

CI runs after publication and again for the exact final integration SHA; pre-merge required checks still gate merge. A missing/skipped/pending check is not PASS. Preserve explicit no-CI policy schema from contract.md, never infer exemption. Native `--completion-contract` is `local-only` or supported repository/PR target; these four mode names are NOT native completion-contract values. Local-only native Done does not waive policy CI or environment gates. A generic native close validator is not a deploy validator.

## Candidate freshness, duplicates and serial coordination
Before EVERY admission and side effect re-read candidate/base/target state, policy, actual approval/window, previous receipts and exact worker state. Changed candidate/base/plan/scope/policy/environment/action packet invalidates affected review/tests/approval; do not transplant old bindings. Local commit changes HEAD: record the reviewed precommit manifest to resulting commit mapping, recompute the contract identity and obtain required reconfirmation; never silently rebind. Merge/squash similarly needs a proven mapping and final-SHA checks. Unknown or concurrent edits => park for ownership resolution.

Stable job identity is source-board + source-outcome/task + candidate digest + mode + target repo/ref/environment + operation packet digest; stage action identity adds stage/action kind. Use a deterministic encoding and SHA-256; retain the exact fields beside it. Search existing outcome records and Delivery tasks, including archived history, before creation; use supported `--idempotency-key` for non-archived card reuse and compare the returned ID's full binding/assignee/status/budgets. Native dedup does NOT cover archived cards or external effects. Same key but changed payload => block, never reuse silently. A mode upgrade is a newly approved scope linked to prior receipts, not permission to redo earlier effects.

Maintain one coordinator-owned serial queue in existing Delivery outcome comments/artifacts, not a new service. Conflict keys: canonical repository + destination branch/ref, and environment + service/resource set; same candidate directory also conflicts. Jobs sharing ANY key run serially across stages and across all source boards. Before release inspect all in-flight/uncertain jobs and active candidate owners. Same branch across different environments still conflicts; same environment/service across repositories still conflicts. Disjoint repo/ref/environment resources and separate candidates may proceed in parallel within existing dispatcher limits. Board separation itself does not protect Git branches or clusters.

This is cooperative admission, NOT a lock, lease, CAS or exactly-once guarantee. If another coordinator/manual owner is active or state is uncertain, park and reconcile instead of claiming exclusive ownership. Prevent duplicate side effects procedurally: persist intent, perform one authorized action, read exact target, persist receipt. On timeout/ambiguous result mark uncertain, do read-only reconciliation (commit/ref/PR/check/deployment identity); never blindly repeat push/PR/merge/deploy. If existence/absence cannot be established safely, block with owner and resume condition. Never launch a duplicate as recovery.

## Finite recovery and closure
Before admission record a role-sized total wall budget, remaining worker admissions, bounded read/poll count, checkpoint and wrap-up reserve; unknown consumption is not zero. Use finite `--max-runtime` and `--max-retries 1` on side-effecting stages (no native automatic failure retry); still inspect infrastructure/reclaim paths, because the breaker is not a lifetime cap. Max one evidence-changing recovery per blocker within the original budget, only after exact worker idle and effect reconciliation. Existing two-rejection/earlier severe recurrence guard remains binding. Expired authority, actual denial, stale candidate, budget exhaustion, ambiguous side effect or no progress => stop; do not reset by new task/mode/run. CI polling must end in a finite recorded observation count and deadline, not endless waits.

Report separate evidence levels: prepared, approved, local-committed, pr-published, integrated, CI-verified (or CI-EXEMPT), deployed, environment-accepted. Commit-only requires actual local commit and clean owned-scope evidence, not push. Publish-pr requires exact remote branch/PR readback and applicable CI for its SHA, never merged. Integrate requires actual target SHA/mapping and final CI or explicit exemption, never deployment inferred from merge. Full-delivery requires deployed identity mapping AND original acceptance observed in the named environment. Source Done, green CI, a completed worker or static fixture cannot substitute. Cleanup remains a separate exact-target approval and existing Cleaner workflow. Close the user outcome only at its requested evidence level; lower-stage success must retain pending higher requirements.

## Verification limit
This is maintained instruction policy, not installed runtime enforcement. Static tests exercise document consistency and synthetic decisions only. Installation, consumer loading, real workers, actual delivery, native wake continuation and original acceptance must each be reported separately. Do not run live canaries, network, credentials or delivery merely to validate this staged package.
