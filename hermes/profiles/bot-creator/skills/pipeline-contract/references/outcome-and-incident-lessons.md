## Outcome-oriented incident coordination

One outcome-owned assignment authorizes the bounded workflow actually requested, not just the next tool invocation. Record a phase authority envelope once: non-secret repository inspection; selected-field safe read-only metadata/config discovery; local artifact, runner and code implementation in owned candidates after existing Git gates; independent review and offline testing. Continue within that envelope without asking for each read, tool, review or routing hop. Permission to implement is NOT permission to execute production changes, publish, access secrets, or run production experiments. A substantive scope/risk change still requires a human decision; an unchanged blocker does not justify automatic retry.

Keep the user's application outcome on the critical path, not improvements to the orchestration platform. If an authorized parent can safely perform a missing admission through its supported surface, apply that bounded action and continue substantive work. Missing worker management tools are a parent-assisted coordination requirement, not authorization for Hermes source engineering—even in parallel. Do not serialize repeated design, delegation and review rounds ahead of an already-authorized implementation merely to make coordination fully autonomous. Before launching any workflow maintenance, identify the concrete application action it enables; otherwise defer it. Stop a maintenance approach that repeatedly generates prerequisite work instead of advancing that action.

Orchestrator owns the complete outcome and resumes the next admitted phase after each useful checkpoint/verdict. First classify the blocker as missing evidence, missing capability, missing authorization or coordination state; state the exact next action and responsible actor. Execute an already-authorized local preparation/admission rather than repeatedly telling the user it needs doing. A DM acknowledgement or a comment recording a decision is not a work admission: read back the actual card and run before saying work started. Reuse existing specialist cards and evidence; do not generate read/review/routing cards for trivial probes. Checkpoints must contain evidence paths, eliminated hypotheses, remaining risk, and the next already-authorized action with admission status. A completed routing card is not an outcome. Keep one consolidated exact reviewed execution decision at the next genuine external-risk boundary, with executor, target, artifact digest, commands, bounds, expected evidence and rollback; do not seek approval for placeholders.

Treat a proposed diagnostic setup as an option, not a mandatory architecture. Before commissioning or repairing diagnostic tooling, identify the original failing application operation, the hypothesis the tool will distinguish, and the concrete remediation decision its result enables. Prefer a bounded use of existing tools when it can answer that question safely; repairing a custom probe is not an application fix merely because the probe has a real defect. Park optional tooling whose repair displaces the original outcome. When the user suggests starting over after repeated diagnosis, reset the approach while retaining evidence, rejected hypotheses, candidates and history; do not repeat discovery from zero. In status reports, lead with whether the current work is an application fix, a diagnostic test, or workflow repair, and state whether real acceptance has run. Tie every proposed fix or test to the specific observed failure; a demonstrated adjacent defect is not a justified substitute when the failing path already passed that stage. Choose the simplest safe discriminating approach using existing approved resources where sufficient; new pods, policies or infrastructure require demonstrated necessity and scoped approval. If inherited experiment constraints prevent an executable test, identify the smallest justified alternative and its changed risk/approval requirements; do not silently weaken bounds or repeatedly build generic controls around an unproven architecture. Discover non-secret image/config/routing/client facts safely with tools, not hypothetical human-owner attestations. Ask a real owner only for a fact inaccessible within authorized scope, a policy choice or a meaningful permission change. Never expose secrets to avoid asking. Selected-field reads must exclude Secret data, inline environment values, tokens, raw logs and kubeconfig; stop on sensitive ambiguity rather than dumping objects.
For this user's incident workflows, drive toward the original real-world acceptance, not repeated planning/research completions. Check executor identity, actual resource availability and permitted operations at intake, before expanding a full downstream graph; late prerequisite discovery creates a board of parked cards instead of progress. Create only the next actionable stages and necessary acceptance/gate records until those prerequisites are known. Represent dependency waiting separately from genuine missing-input/capability blocks using supported states; verify parents and admission rules before changing status, because automatic promotion can race. Never blindly unblock downstream cards to improve the board's appearance. When a card appears in triage after previously running, inspect its event history and recurrence classification before treating it as new intake: repeated capability blocks can trigger automatic escalation. Preserve completed specialist results and the outcome owner's identity; resolve the concrete admission gap before resuming, rather than promoting the unchanged card into another blocked attempt.

After each verdict, execute the next already-authorized stage in the same coordinator event turn, or prepare and present the exact external-risk approval request before waiting. Preparing that request is already-authorized coordination, not a permission-gated action. Do not stop at a local-acceptance comment or wait for the user to ask why nothing is running. After approval, bind it to the concrete packet/candidate and verify downstream admission; do not ask again for covered internal steps. Ask only for a new concrete risk or permission decision. Separate document quality from execution readiness: approving an accurate list of missing prerequisites does not approve a runnable experiment. If a packet is not executable, route directly to a bounded capability/resource check or a concrete setup decision, not another planning-and-review loop. Before admitting local-only packet preparation, check whether its required inputs can actually be obtained within that scope. Do not prescribe elaborate manifests whose image compatibility, transport endpoints, routing enforcement and cleanup interfaces are all unknown, then treat reviewed placeholders as operational progress. When narrow metadata reads cannot resolve these gaps, first compare the needed work with the current task authority envelope. If bounded non-secret discovery and local implementation/testing are already authorized, admit that substantive phase without another permission question; otherwise request the missing scope once. Keep cluster mutation and experiment approval at their actual risk boundary. Do not invent image/network/credential owners or require owner attestations where no actual owner has been identified. Native reviewer approval of an accurately incomplete packet proves document quality, not execution readiness. When nothing is running, report the single next actionable blocker and owner, not the entire downstream waiting list. For an apparently frozen Todo card, inspect its prerequisite states before diagnosing dispatcher failure; surface the blocking prerequisite and concrete decision promptly instead of leaving the user to discover an idle queue. Re-read current runs before repeating a status update, because a previously running review may already have completed. Consolidate unresolved production-access requirements into one actionable approval packet with exact targets, executor, commands, bounds, expected evidence and rollback. Keep preparatory work distinct from executing that packet. Do not compensate for a failed handoff by spawning another full investigation.

When a teammate completion contains no usable reply, inspect the exact board and task records read-only before assuming failure or resending: external changes may have succeeded even though the message output was empty. Report verified active work, its next decision and genuine blockers rather than a chain of unverified intentions.
