# Read-only Forgejo CI verification

## Procedure
1. Resolve the exact forge host, repository, branch/ref, candidate SHA and required workflow/status names from the task's delivery policy. Inspect that Forgejo deployment's API schema rather than assuming GitHub CLI compatibility or uniform Forgejo versions.
2. Obtain explicit authorization for the credential transport. Consume a token in memory from the approved source; do not copy it into another profile, print it, or place it in command-line arguments. Keep the helper fixed to the approved HTTPS host, GET-only, with redirects and ambient proxies disabled, bounded timeouts and request counts, no automatic retries, and sanitized errors.
3. Test authentication separately with a minimal read-only endpoint. Classify an anonymous HTTP 403 separately from a local execution-guard denial. When existing scope permits configured authentication, diagnose the transport and use the maintained authenticated fixed-host reader once; do not repeat anonymous requests, expose the token or treat this as permission to bypass a tool denial. Report authentication success only as access verification, not proof that a repository's CI passed. Avoid enumerating private repositories when a scoped repository was not supplied.
4. Fetch paginated action-run and commit-status evidence for the exact candidate. Validate returned repository/ref/SHA identity instead of trusting query filters. Determine the latest applicable attempt; an earlier successful attempt must not hide a later failure.
5. Require a nonempty expected-check policy and evidence for every required check. Missing, pending, skipped, cancelled, unknown or failed checks must not become PASS. If the API cannot provide historical job/attempt evidence required by policy, stop with NOT VERIFIED rather than weakening the policy.
6. Re-read the target ref after collecting checks to detect movement. After merge, squash or a final bookkeeping commit, verify the resulting SHA again; PR-head success is not post-integration success. Select premerge versus postmerge evidence explicitly: derive each phase's required contexts from its actual workflow triggers, because protected PR checks need not run on a push. Preserve requested and observed refs separately; accept only documented alias relationships and reject malformed identifiers rather than trimming or repairing them. Report branch-head verification as such; do not claim PR-number/head/base binding unless the helper actually fetched and checked that PR object.
7. Emit structured evidence with repository, exact SHA, required checks, observed results, run identifiers/URLs and observation source. Do not dispatch, retry, merge or push from a read-only watcher. Keep deliberate no-CI exceptions in an explicit approved policy, distinct from successful CI.

## Bounded verification execution contract
Before admitting CI verification, bind the maintained helper's exact path/version and permitted arguments, credential source and fixed host/repository/SHA to the packet. Confirm the worker actually exposes native read_file and the approved helper interface; a missing interface is a preflight failure, not an invitation to improvise. Use native read_file for local evidence, with bounded pagination. Do not invoke inline python -c or equivalent arbitrary execution merely to inspect local JSON.

A real execution denial stops that action and its substitutions. Preserve the denied operation and any subsequent violation. Only an explicit reviewed interface disposition can authorize a different interface; do not treat this standing preference as retroactive approval or automatic denial recovery. An independently approved fixed GET helper is not permission to bypass a denial affecting that helper, its network target or credentials.

Separate PR-head/premerge and merged-SHA/postmerge required contexts in the admission packet using maintained workflow trigger evidence. Do not discover this distinction by repeatedly rerunning mismatched verification. Require nonempty policy, exact identity/latest-attempt checks and final target freshness; existing successful output never implies an exemption.

For each admitted stage align its procedural allowance with its native timeout inside the remaining cumulative window; reserve artifact-writing and verdict time before spending the full allowance on reads/polls. Persist bounded structured observations after each successful helper batch and emit the final artifact and native verdict before wrap-up reserve expires. Use retained immutable evidence rather than reconstructing full history; refresh only mutable identity/status/authority at the action boundary. A timed-out run with partial green output remains incomplete, not CI-approved.

Recovery must reconcile exact prior worker idle and ambiguous effects before admission. Preserve timeout, denial, retries and consumed time. Ordinary authorized remaining capacity may be used only if existing policy permits; an exhausted or expired window requires explicit bounded continuation authority recorded separately from the old window. Never raise retry limits, rename work to reset them, or launch a duplicate owner. An approved verification-only recovery does not authorize repeating publication/merge or adding cluster mutations.

## Delivery-policy preflight

Before requesting publication/deployment approval:
1. Read the exact target branch, branch-protection settings and emitted workflow/status names through the authorized read-only interface. Inspect workflow trigger definitions as well: a check that runs only after merge cannot serve as premerge evidence.
2. Compare actual enforcement with the proposed delivery contract. An unprotected branch or empty required-context list is a policy mismatch, not CI success. Derive required names from real workflow/status evidence; never invent them or accept an empty list as satisfying protected delivery.
3. If protection must change, present one scoped repository-policy decision. Read-only CI Watcher reports the mismatch; an explicitly authorized write-capable executor changes only the approved branch settings, preserving unrelated collaborators and policy, then reads back the exact remote target. Do not claim configuration succeeded from an API write response alone.
4. If local merge plus push is permitted, check whether branch protection allows that route without exemption. Otherwise retain protected PR integration; route permission is not authority to disable controls or force-push. Verify the final integrated SHA, build/image identity and deployment revision separately.
5. Bind delivery dependencies to the reviewed candidate's actual owned worktree. If an immutable old task points at unrelated dirty work, keep it parked and create only the necessary correctly bound substantive replacement; preserve history and verify replacement edges before releasing work.

## Verification
Use offline fixtures for exact-match success, wrong SHA/ref/repository, stale evidence, empty requirements, missing checks, every nonpassing state, later failed attempts, pagination, HTTP failures, and ref movement. Label fixture results as offline tests. Run a separate authorized live authentication check; only a scoped live candidate check can establish production CI status.

Reuse the installed CI watcher's maintained helper and tests when available; inspect its current help and API limitations before invoking it. Do not duplicate a helper into each consumer profile merely to make it discoverable.

## Registry evidence projection and adversarial fixtures
For downstream image evidence, distinguish the digest of exact fetched bytes, an OCI index digest, platform-manifest digests and descriptor assertions. Hash exact input bytes before classification; a child descriptor does not verify the child's content. Keep unknown platforms unclassified, handle null/missing fields explicitly and never equate a selected SLSA revision with cryptographic provenance verification.

Before activating a projection, test one valid object, multiple concatenated JSON values, null followed by valid evidence, malformed trailing data, oversized aggregate input, descriptor-count limits and aggregate output limits. Enforce bounds across the entire stream, not per object: parsers may otherwise emit arbitrarily many individually valid records. Suppress raw config/history and parser/producer stderr, emit only bounded selected fields, and reject partial evidence on failure. Capture and preserve the producer's exact exit status separately from parser status; pipefail alone proves nonzero failure, not exact upstream-status retention. Verify a synthetic nonzero producer status with both valid and malformed downstream data. Keep these offline fixture results distinct from live registry evidence.
