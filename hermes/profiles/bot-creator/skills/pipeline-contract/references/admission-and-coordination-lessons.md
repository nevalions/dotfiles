## Admission and coordination discipline
Load [canonical coordinator management](coordinator-management.md) for native event subscriptions and authenticated non-worker board recovery. Use the existing Desktop/gateway protocol; no new service, core patch or stored credential is needed. Before release, verify the subscription for the exact current specialist card—not merely that historical cards have subscriptions—and explicitly assign the intended worker while parked. Treat READY as execution admission, never as an inert temporary state.
Use the canonical non-worker Orchestrator Bot Chat for event-driven board management, not a dispatcher-owned coordinator worker merely to route tasks. Native local notify+wake subscriptions can wake that chat; bind and read back exact board/task/chat/profile identities on specialist admission. On each event inspect retained evidence and choose the next in-scope action without a human micro-approval. Worker tool restrictions remain binding; never strip worker identity or use CLI/API to evade a denied worker call. CLI unblock/promote do not recover triage, but the documented authenticated board status PATCH supports triage->todo/ready from an authorized non-worker context. Verify dependency/authority/budget/idle prerequisites and actual API availability before using it. Do not falsely claim that native triage recovery is absent or replace cards merely because one CLI command does not support it. Subscription setup, actual wake, successful management, worker continuation and closure are separate verification criteria; report missing links honestly. No Hermes source modification is permitted.
Before assigning coordination, enumerate the exact board mutations needed by the next substantive stages and verify them in the actual intended coordinator context, separately from specialist-worker capabilities and the parent CLI: can it create substantive tasks with required retry/runtime controls, edit existing assignments, repair dependencies and release authorized stages? Verify the supported authenticated connection and target-board selection as well as endpoint documentation; a documented transition without an established transport is not an available recovery capability. Map each required operation to a verified worker capability or a designated supported parent action. A partial management patch is not sufficient merely because it adds creation or editing; check whether the existing graph also needs adoption, dependency removal or unblock before dispatching the coordinator again. Check effective tool schemas and execution policy; CLI availability on the host does not grant a worker permission to use it. If required management operations are missing, designate an authorized parent/operator to perform exact scoped admissions and return readbacks; do not discover this gap after repeatedly dispatching routing-only work or ask the user to reapprove an already-authorized phase. Never retry a denied tool or use shell/API/database access to bypass a worker restriction. Follow the parent-assisted admission recipe in [worker progress](worker-progress.md).

Treat a multi-step parent admission as a sequence of independently verified transitions, not an all-or-nothing script. If a later command fails, read back the exact affected cards and edges before continuing: earlier mutations may already have succeeded. Never replay the whole script blindly or equate its final exit code with the status of every action. Inspect the installed transition's accepted source states before moving a triaged owner; a command that handles blocked cards need not handle triage. If specialist admission is valid but outcome-owner recovery is not, preserve the owner and report that separate limitation rather than withholding already-authorized substantive work or force-changing status.

Prepare candidate worktrees and verify the installed creation interface before creating runnable cards. Inspect existing workspace ownership and parked diffs before selecting a reusable card; never assign a new fix over another task's unfinished edits. Reuse a card only when its editable scope, workspace and lifecycle actually fit. If completed preparation must stay immutable or a production-execution card must retain its approval dependency, a separate bounded substantive preparation card is justified; record why reuse is unsafe, keep the same outcome owner and avoid a routing-only intermediary. Set workspace binding, parent dependencies, native runtime and failure/retry limits at creation; creation support does not imply those fields can later be edited. Keep incomplete admissions parked, and distinguish prepared evidence, a ready card, an admitted worker and a completed result in every status report. If required fields cannot be changed through supported editing, prefer a correctly configured replacement created BLOCKED over ad hoc database mutation. Verify replacement prerequisite edges before removing superseded edges; retain failed cards as labeled history, not permanent blockers of final acceptance. Never remove a gate merely to make the board move: validate the replacement evidence first.

Before dispatching a prepared assignment, render one authoritative task body: remove draft-only instructions such as "not created" and resolve conditional permissions against the actual user approval instead of prepending contradictory overrides. State the deliverables, allowed writes, excluded operations, exact workspace, review handoff and stop conditions. For local operational packets that do not edit a repository, use a retained task-owned directory with native `dir` binding; do not manufacture a Git checkout or write into the application's candidate merely to hold proposals. Require real files and offline checks, and label unresolved manifests non-applicable rather than asking approval for placeholders.

Before releasing preparation, retain an outcome-owned Orchestrator continuation and verify its supported resumption path so reviewed artifacts have a next action. Reuse existing dependencies rather than creating another routing-only card for each batch. When substantive work must finish before the owner resumes, link the specialist prerequisite to the existing outcome card, never both directions; preserve the owner and its attempts instead of replacing it with another routing card. Verify persisted assignee, workspace, parents, runtime and retry limit, then read the run record separately: READY means queued, not started. Distinguish successfully setting up dependency waiting from observing automatic resumption after completion; the former alone does not prove the latter. Keep a human execution gate blocked when local preparation completes; static review validates artifacts, not production authority.

Send Orchestrator a complete bounded handoff containing the authorized local preparation, evidence paths, required card settings, acceptance dependencies and concrete return evidence. Avoid spending finite bot-to-bot exchanges on repeated permission requests for already-authorized planning. Keep production and publication approval separate. If messaging hits its loop guard, do not resend or route around it; state exactly which instruction was not delivered and preserve the remaining action for an authorized continuation.
