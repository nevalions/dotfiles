# Diagnosing apparently stalled Kanban work

## Read-only triage
1. Discover the actual board with `hermes kanban boards list`; use `--board <slug>` on every subsequent command. The current board can be empty while the work runs elsewhere; do not switch global board state just to inspect it.
2. Inspect selected task metadata through a verified non-promoting read surface. Do not assume `list --json` or native `kanban_list` is read-only: inspected versions call `recompute_ready`. For strictly read-only triage, prefer authenticated native GET for a verified existing unarchived board with an existing database; its initializing connection is not a guarantee of zero storage effects. Where authorized, selected-field SQLite `mode=ro` inspection is an observation fallback, never a mutation or worker-fence bypass. Record assignee, status, start time, dependencies, allowed diagnostics and configured runtime limit. Read the assignment before judging duration: production probes and source inspection are broader than ordinary web research.
3. Start with `hermes kanban --board <slug> runs <task-id>`, `diagnostics`, and `hermes gateway status`. Treat even run summaries and crash-event output as potentially sensitive: production commands can leave configuration fragments in their tails. Inspect worker logs through a local allowlisting/redaction step before returning content; do not print a raw `log` tail or full `show` output by default. Derive elapsed time with a clock/tool, not mental estimation. Use installed help if syntax differs.
4. Follow the actual attempt's worker session ID returned by `runs`. A card's `session_id` may identify its originating Orchestrator chat, not the executing worker. Do not attribute origin-chat inactivity to the worker.
5. If the worker log contains only a session handle, inspect the owner-profile session through supported read-only RPCs or its SQLite database opened with `mode=ro`. Inspect table schemas first. Start with session activity timestamp/description and recent message timestamps, tool names and content lengths; fetch only selected relevant paths or sanitized evidence afterward. Do not dump complete prompts, tool arguments, production configs or signed URLs merely to prove activity.
6. Correlate last tool results, current provider activity and tangible artifacts. Distinguish active investigation, waiting for a model response, a long-running subprocess, external-access failure, repeated unproductive probes, and stale ownership. No diagnostics is absence of a reported error, not proof of healthy progress.
7. Report the exact stage and age, last meaningful action, known evidence gap and budget status. Separate verified observation from suspected cause. Do not promise a completion time from tool counts.

## Intervention and observability
Preserve the existing attempt while evidence shows recent activity. Do not reclaim, restart, reassign or start a duplicate worker merely because the UI is quiet. If intervention is warranted, use supported task/session controls within the user's authorization and preserve partial artifacts before changing ownership. A Bot Chat message is not automatically steering for a separate Kanban worker session.

Require future worker assignments to publish concise durable checkpoints at an explicit cadence and on stage changes. Keep checkpoint content sanitized and decision-oriented; repeated "still working" comments are not evidence. Record intended execution budget separately from its enforced runtime setting and verify both on admission. Do not claim the timeout is enforced until the installed dispatcher/runtime path has been checked.

## Scoped stop and controlled restart
Keep the following live transitions in the authorized parent session. Delegated children can prepare revised bodies, scripts and diagnostic reports, but native Kanban write fences can refuse their mutations. Do not strip delegation markers, bypass a fence, or treat a prepared script as an applied change; the parent must inspect it, execute permitted operations and verify the exact target.

1. On explicit stop authorization, park the exact card with `hermes kanban --board <slug> block <task-id> --kind needs_input "<reason>"` and verify its state. A dependency block may auto-promote; use a human-held state for a deliberate pause.
2. Load `scoped-session-stop` to interrupt the exact worker through the existing authenticated gateway endpoint. Verify idle state and pending requests separately from board state: ending a claim does not itself prove model execution stopped. Never restart the whole gateway to stop one task.
3. Preserve the sanitized report, evidence manifest and artifact hashes outside disposable task workspaces. Record unresolved hypotheses and contradictory findings without presenting them as reviewed conclusions.
4. Before restarting the same card, update its current body through the supported edit surface. Explicitly supersede the old broad scope, identify preserved inputs, forbid unwanted new probes, specify a short deliverable and review handoff, and require progress checkpoints. Retained attempt history can still contain earlier instructions; make the current scope authoritative.
5. Verify budget and retry controls on the existing card before release. Inspect edit/API support separately from creation support: a flag accepted by `create` is not evidence that `edit` accepts it. Do not substitute a profile-wide setting that affects unrelated tasks or write an unverified direct-database recipe. If editing cannot set the required fields, prepare a replacement using supported creation: create it BLOCKED with the exact retained workspace, parents, runtime and retry settings; verify them; add and read back each replacement downstream prerequisite BEFORE unlinking the superseded edge. Label the old card superseded and preserve its failed runs/artifacts; never fake successful completion. Release the replacement only after validating its scope and evidence. If safe blocked creation or dependency repair is unsupported, keep it parked and report that precise gap.
6. Distinguish behavioral tool-call limits, cooperative model run budgets, and dispatcher watchdog timeouts. Verify timeout failure/requeue semantics; a short timeout without a retry bound can cause repeated expensive attempts.
7. Only after scope and controls are read back, use `hermes kanban --board <slug> unblock <task-id> --reason "<revised scope and authorization>"`. Read `runs <task-id>` to establish a new attempt and its actual session. If admission has not occurred, report ready/queued rather than running. No history reset or gateway restart is required merely to reuse the card.

## Approved immutable-binding setup-error recovery

Use only canonical non-worker Orchestrator or its disclosed authorized parent, after an explicit bounded recovery decision. This repairs admission setup, not rejection semantics or user scope. Check installed create/edit/link/unlink schemas; creation support does not establish edit support. A denial is not a setup-error workaround authorization.

1. Reconcile the existing outcome/action identity, authority and source and replacement history first. Preserve verdicts, failed runs, evidence and cumulative consumed budget. Duplicate intent => reconcile the existing target, not another card. Ambiguous create/link/unlink => uncertain; inspect the exact target and edges before any retry. No reset by new task/run IDs. Unknown history, unknown worker state or concurrent writers => parked, not admitted.
2. Require old worker verified idle (including pending requests) and old card parked in a human-held state with readback before any replacement release. Card status alone is not idle proof. Preserve the old source as superseded evidence, with no fake completion or approval.
3. Verify the same candidate exact digest at the existing durable path. With supported creation make one scoped replacement execution card initially BLOCKED, native `dir` bound to that path, explicit assignee/independent reviewer, finite runtime/retry controls and current narrow assignment. Read back all persisted bindings before release. Do not replan, create a new outcome owner, recopy a divergent candidate or restore removable scratch ownership.
4. Link old source/outcome IDs, source history references and digest, failed findings, authority/amendment reference, original start, cumulative consumption and remaining correction/review allowance in the replacement and existing outcome record. History links are evidence references, not a dependency on the superseded parked source. Run existing review-loop guard on the complete combined history; keep original sequence and provenance with an external source/run mapping if run IDs need disambiguation. The README-style expired allowance needs the explicit separately bounded amendment in [review-loop guard](review-loop-guard.md), not a reset or a forged CONTINUE.
5. Repair only same-board dependency edges using supported create/link/unlink operations with exact readback: retain applicable upstream prerequisites; link replacement as prerequisite of each affected downstream card and verify it BEFORE unlinking the superseded prerequisite. Verify no cycle, no cross-board edges and no unintended READY/admission window. Preserve unrelated edges. The replacement must not depend on the parked source it supersedes. If safe blocked creation or link/unlink is unsupported, leave parked and report the precise gap; never write the DB.
6. Recheck candidate digest, idle ownership, authority, budget, independent review and repaired edges at release. Release only the scoped replacement through supported parent controls, read back card and actual run/session, and retain the old parked card. Queued is not running. Candidate digest may change only during the authorized correction; final tests and independent rereview bind its resulting exact digest. A second rejection, severe recurrence, denial, exhaustion or uncertainty stops recovery. No publication, credentials/cookies or cluster operations are implied by setup recovery.

## Parent-assisted admission when worker management differs

Use this path for an already-authorized phase when the worker's permitted tool surface cannot perform a required admission. Treat the limitation as a capability gap, not missing user permission; recheck capabilities on future use instead of recording permanent tool unavailability.

1. Read the worker's durable checkpoint and prepared substantive assignment. Verify the stopped attempt's outcome and ensure no competing admission is active. Preserve scope, reviewed artifacts and existing outcome ownership.
2. Inspect the worker's effective schemas and protocol, and separately inspect the parent's supported CLI help. Confirm which operation or creation field is missing. Do not instruct the restricted worker to shell out, strip execution markers or call an alternate API to circumvent its policy.
3. In the authorized parent surface, create the substantive prerequisite initially blocked with an idempotency key, exact assignee, retained `dir:` workspace, skills, completion contract, native runtime and retry limit. Use `hermes kanban --board <board> create ... --initial-status blocked --max-runtime <duration> --max-retries 1 --idempotency-key <key>` only after checking installed syntax. Read back the persisted fields; inspect existing ownership before reusing a directory.
4. Build truthful admission evidence from those readbacks and the actual task authority, not a copied test fixture. Run the applicable validator before release. Record phase budgets separately from the native total runtime. A procedural reviewer budget is not a different watchdog: verify how native review uses the stored runtime and disclose any distinction rather than claiming an unconfigured limit.
5. Link the substantive prerequisite to the existing outcome owner with `hermes kanban --board <board> link <specialist> <owner>`. Verify the edge and absence of a cycle; the specialist must not depend on that owner. Record admission evidence and remaining management limitations on the owner.
6. Unblock the owner through the authorized parent so it waits on the incomplete prerequisite, then release the validated specialist. Read back both states and inspect the specialist's run record. Report queued versus actually running accurately; do not restart the gateway or create a replacement routing owner.
7. After substantive completion/review, verify the same outcome owner resumes. Parent-assisted admission resolves only those operations actually performed; it does not install missing worker tools, prove future automatic dependency handoffs, or authorize later production actions. Route any remaining required management operation to the designated parent once, with exact changes and evidence, rather than entering unchanged retries.

## A restarted attempt immediately blocks again
1. Read the latest attempt outcome and events, not just the card status. Separate an intentional worker block, timeout, nonzero process exit, admission failure and protocol failure.
2. Compare actual elapsed time with the configured limit. An early nonzero exit is not evidence that the time budget killed the worker.
3. Inspect the failure-breaker event separately: a first-failure policy can correctly park a crashed attempt. Keep that safeguard while diagnosing; do not increase retries merely to hide repeated failures.
4. Locate the new attempt's own session and error boundary. A captured output tail may be an earlier successful tool result rather than an exception. Extract sanitized error types, timestamps and tool names before reading narrowly selected context. Do not infer root cause from an unrelated configuration fragment.
5. Before rerunning a timed-out author, inspect durable outputs and the exact write-tool result: a complete artifact can survive while the terminal handoff fails. Verify its ending and hash, then verify the original worker is idle independently of board timeout. Recover the existing artifact rather than repeat full planning. Use a supported native review transition only where source-state rules permit; otherwise follow the explicit recovered-plan-review schema for an independent ordinary review card, without claiming native provenance. Once replacement review evidence is accepted, repair downstream edges so the preserved timed-out author is not an unsatisfiable prerequisite.
6. For self-blocking on a call ceiling, inspect which calls consumed the allowance and whether the deliverable is partial; for timeout, distinguish active computation from saved-but-unhanded-off output. Correct admission size or reduce duplicate reads based on that evidence, not by repeatedly raising limits. Keep the card blocked until recovery is verified, preserve prior evidence, and avoid duplicate production probes.

## Edit-first correction after retained review findings

For an authorized correction with exact findings and source citations, perform the smallest factual patch immediately after essential candidate-identity/source checks. Save the corrected artifact before optional formatting or evidence packaging, then run affected checks and independent review. Simplify misleading diagrams instead of spending the author allowance on repeated column/line measurements: unchanged rejected bytes plus formatting-only probes are execution drift, not useful progress. Reuse still-valid checks and retain consumed attempts; an exhausted allowance requires an explicit bounded amendment, not a silent restart.

## Python bootstrap collisions in reused workspaces
A restart can fail before any model session exists because Python starts with the task workspace on its import path. Diagnose this boundary before changing providers, prompts, histories or retry limits.

1. Inspect the sanitized traceback for a standard-library import resolving into a workspace script. Use `importlib.machinery.PathFinder.find_spec('inspect', [workspace])` to check a suspected name without executing it; do not test by importing the suspect script.
2. Inspect the script statically for top-level subprocesses and writes. Accidental imports can execute old diagnostics before the new assignment's restrictions are loaded. Report those unintended side effects separately; absence of a new model session does not prove that nothing ran.
3. With recovery authorization, preserve the colliding source and matching bytecode under non-importable names, such as a quarantine directory with `.disabled` suffixes. Include legacy adjacent `.pyc` and matching `__pycache__` entries. Verify hashes before and after; do not delete diagnostic evidence.
4. Confirm workspace-only resolution no longer finds the module. From the exact task working directory and managed Hermes interpreter, verify standard-library resolution and import `hermes_cli.kanban_worker_client` without invoking its main routine. For an `inspect` collision, assert `callable(inspect.signature)` and that `inspect.__file__` is outside the workspace.
5. Add a sanitized recovery comment, retain the narrowed scope and retry breaker, then unblock only under the user's retry authorization. Read back the new attempt instead of equating an unblock acknowledgement with execution.

Prevent recurrence by giving diagnostic scripts distinctive names and putting executable work behind a main guard. Avoid standard-library names such as `inspect.py`, `json.py` and `logging.py`: model-level instructions cannot protect bootstrap from import-time code. Separate spawn-to-crash bookkeeping duration from actual execution time, because dispatcher detection latency can dominate a startup failure.

## Completion labels
Treat decomposed intake as an administrative milestone, not incident acceptance. Link a distinct final acceptance task to all required gates and retain the original production success conditions there. If diagnosis finishes with alternatives or requires approval for intrusive probes, report that result honestly rather than completing the incident as fixed.
