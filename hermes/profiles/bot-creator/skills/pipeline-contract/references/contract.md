# Pipeline contract v1

## Authority and limits

Installation authorizes workflow preparation, not executing tasks, tracker writes, commits, publication or cleanup. Preserve all existing models. Verify actual roster/tools at dispatch. This contract is instruction policy plus an offline JSON validator; it does not install a core hook or authenticate human identities. `actor_kind=human` is only a supplied assertion: the orchestrator must verify an actual user decision/message. There is no claimed universal `require_review` lock. Do not release a downstream card merely because a parent is DONE: verify evidence first.

## Ordered pipeline

These are applicable gates, NOT a mandate to create a card for every numbered item. The default is one bounded outcome owner, focused local implementation/tests, independent same-card review, and actual acceptance with separate external-risk permission. Planning/research/Beads/wiki/logging are optional supporting work unless required by repository policy or original acceptance; do not put optional work ahead of a supported fix. A concise existing approach can supply plan evidence; never manufacture native plan approval to satisfy a schema. Preserve required evidence gates and report schema mismatch without making core upgrades a prerequisite. Before request_changes or author continuation follow the shared review-loop guard: second rejection or recurring severe finding => native block and existing-owner notification, not another correction dispatch. No Hermes core/runtime edits.

1. **git-puller**: once per repository, run installed safe FF freshness preflight before any edits. Dirty/diverged/detached/missing-upstream/network failure blocks normal editing; never stash/reset/rebase. Preserve branch/base SHA and command evidence. No repeated pull during active work. A separately authorized isolated staging worktree may prepare a patch after failure, but is not a passed preflight or deployed delivery.
2. **beads-coordinator intake**, only if a tracker exists and task tracking is authorized. Read canonical `/home/linroot/.agents/skills/beads/SKILL.md`; choose create vs update with user when unspecified. No automatic initialization. See [Beads adapter](beads-adapter.md).
3. **orchestrator candidate**: native Git worktree, not a plugin. Create an explicitly owned candidate with native Git, then bind EVERY pipeline card to `workspace_kind="dir"`, `workspace_path="/absolute/candidate"` (CLI `--workspace dir:/absolute/candidate`). This is still a Git linked worktree; `dir` describes Kanban lifecycle ownership, not Git topology. See [verified workspace lifecycle](workspace-lifecycle.md). Never register that same checkout as a removable `scratch`/`worktree` parent or unrelated card: completion of a `dir` child can trigger deferred cleanup of a removable parent. Inspect all existing owners first and block on ambiguity. Keep the candidate outside ephemeral managed scratch storage in production; only the separately approved cleaner owns its deletion. Resolve symlinks, repository guidance, status and ownership before creating it. Record canonical repository, exact worktree, branch/base SHA and owned paths. Sequential planner/implementer/reviewer/tester/repo-docs/Commiter use this SAME candidate worktree. A card's default fresh worktree must not silently replace it. Ensure runtime project/card workdir bindings resolve there or block. Preserve uncommitted changes; do not copy only HEAD. Parallel writers require separate worktrees and an explicit integration owner; after integration invalidate old candidate evidence.
4. **operational diagnosis when relevant**: route bounded Kubernetes observations to `diagnostician` (GPT Sol) using its installed MCP, not to wiki/web Researcher. Its current tools cover explicit-namespace pod lists, events and metrics only; they do not provide logs, exec, network experiments, provisioning or deployment. Supply prior diagnosis and exact namespace, cap MCP calls, persist sanitized results through native card comments, and retain the existing outcome-owned Orchestrator continuation so completed observations advance the next authorized phase rather than spawning a routing card per read. Observation success is not root-cause proof or incident resolution. Preserve existing human approval gates for experiments/writes; do not assign unavailable operations to this bot. Recheck live tools at admission.

   **researcher optional**: wiki first, ordinary public web/primary sources next, existing bounded paid fallback only after a material gap remains. Return evidence, alternatives, assumptions and risk; no wiki filing. Skip only with an explicit rationale.
5. **pre-plan risk gate**: orchestrator records low/medium/high with reasons. Medium/high, material ambiguity, destructive/publication/security/data implications require a human decision. Human cards remain BLOCKED and unassigned to automatic decision workers; no worker may complete them as an automated decision. Approval binds scope, plan version (initial empty plan is an explicitly hashed artifact), candidate and action policy. Low risk may proceed with recorded rationale, never unknown risk.
6. **planner (Astra)**: produce exact files, small ordered steps, acceptance commands, expected outcomes, dependencies, risks and stop conditions. Request native review on the SAME planner card and stop. Reviewer approves with native `kanban_complete` plus `review_outcome=approved`, which completes the source card. Changes return through native `kanban_request_changes` only in review-origin context. A distinct orchestrator dependency owns next-stage admission. Only when a complete preserved plan survives a verified timed-out author attempt may the explicit [recovered plan artifact review](recovered-plan-review.md) path substitute a separately completed independent ordinary-card review; never label it native or falsify author completion.
7. **post-plan risk gate**: re-evaluate risk at phase level. Existing user task authority may cover bounded local implementation, review and offline tests; do not ask again for each safe read or ordinary in-scope implementation step. Non-low-risk actions still require truthful human authorization records bound to the reviewed plan/candidate under the evidence schema; ask again for material risk/scope changes, not merely to route work. Changed scope/plan/policy invalidates old bound evidence; preserve it and obtain applicable reconfirmation rather than silently transplant it. Production execution/publication is never inferred from implementation authority.
8. **main-implementer (Kimi)**: verify prior preflight rather than pull again; implement with tests in the same candidate; native reviewer on SAME implementation card; never direct-to-Commiter default. Reviewer verifies actual artifacts and exact candidate digest, not prose.
9. **tester + browser-tester**: explicit PASS with command/exit/output evidence, browser when applicable. FAIL/UNKNOWN/SKIPPED is not PASS and must not complete a PASS gate. Orchestrator creates correction work from the implementation/review parent, NOT dependent on the blocked test card (avoid a cycle); retest after correction. A tester is not a native review-origin worker and must not impersonate one.
10. **repo-docs before delivery**: update required repository docs. If any candidate content changes, recompute digest and repeat affected review/tests (conservative default: all). No delivery until evidence matches final candidate.
11. **orchestrator acceptance**: map every criterion to fresh evidence and revalidate `deliver`. **wiki-skill** writes only the explicitly authorized task summary under RW; RO remains untouched. Repository docs belong before delivery, wiki summary is separate. Neither research nor installation grants wiki write permission.
12. **Commiter**: ask for repository-specific delivery policy if absent. Persist exact repository, branch/ref, allowed commit/push/PR/merge actions, remote, scope, human decision reference and limits in task evidence. Do not infer push/PR/merge from implementation permission, nor escalate when a path fails. Preserve delivery skills but apply these gates first. Inspect remote provider: Forgejo CI is external API/CLI evidence, not GitHub `gh` proof. Existing repo-specific no-CI policy requires a separately verified human `ci-exemption` authorization bound to the exact candidate, final SHA, repository and delivery target, with existing user-policy evidence. Use the explicit EXEMPT schema below; never fabricate PASS or interpret missing/skipped checks as exemption. Record delivered SHA AND resulting integration SHA and verify actual remote refs.
13. **ci-watcher**: read actual required checks for exact resulting SHA (or delivered SHA if no integration). Missing, skipped, pending, failed or a different SHA blocks closure. The sole no-CI alternative is an explicitly authorized EXEMPT record under the schema below, not inferred absence. Record provider, run URL/id, names and statuses. Never treat lack of GitHub checks as Forgejo success.
14. **Beads close**: only after verified delivery/CI; current session must actually own issue. Different actor/session requires explicit recorded owner release/transfer and successful new claim, never copying the actor string. Read back exact issue. Closure is not Git delivery evidence.
15. Any final bookkeeping commit after CI invalidates that CI evidence. Deliver under the same allowed policy, read final SHA and run CI again before cleanup/final success; changed content also invalidates candidate approval/test evidence.
16. **cleaner**: dry-run inventory first (exact worktrees, branches, refs/SHAs, ignored/untracked files, ownership, integration/delivery/CI status). Require fresh scoped human approval for exact targets, preserve unrelated work and useful ignored files. No blanket prune/delete; recheck immediately before action and read back afterward.

## Production incidents: deployment and final acceptance

For a production incident, repository delivery/CI is not resolution. Include explicit **deployment** and **production acceptance** stages/cards in the DAG before dispatch, and keep incident final acceptance blocked until both succeed. If an existing DAG lacks them, Orchestrator must correct dependency wiring through supported transitions rather than treating a repository `close` PASS as incident success.

Deployment requires a separately verified user authorization scoped to environment, service/repository, target SHA, allowed operations, rollback and limits. Workflow-recovery authorization, planning/implementation permission and commit/push/merge policy do not confer deployment authority. Without that authorization, prepare evidence and keep deployment blocked; do not execute it. Record deployment attempt, commands/exits, environment and actual running/deployed SHA, and read back the exact target. Prove how deployed SHA maps to reviewed final integration SHA; a pushed branch is not proof of a running deployment.

Production acceptance must bind that deployment and the original incident criteria to fresh observed results. For row/file incidents, specify the expected production row identity and field values, expected file path/content or digest, and deployed SHA **before** testing; read back actual production row/file and compare expected versus observed with timestamps and evidence references. State genuinely inapplicable criteria explicitly with reasons, never silently omit them. Failed, unknown, missing or stale results keep incident closure blocked. Separate authorized production execution from read-only preparation; do not expand production access or data-changing commands to satisfy this contract.

**Validator boundary:** existing `deliver`/`close`/`cleanup` stages remain repository gates for compatibility. This change adds no `deploy` CLI stage or optional flag that could silently waive acceptance. Deployment/production-acceptance records are required caller-enforced incident policy, not currently machine-validated by this standalone validator. A `close` PASS alone never proves production success. Preserve existing evidence semantics rather than retroactively interpreting repository `acceptance` as production verification.

## Role-sized execution budgets

At admission, size each role's runtime and call ceiling for repository breadth, required skills, evidence reads, implementation/tests, review and terminal handoff; record checkpoints, wrap-up reserve and exhaustion handling. Research's five-minute fallback triage cap is not a universal diagnostic/planner/reviewer/implementer/deployment cap; use explicitly justified finite task-scoped diagnostic budgets where appropriate. The earlier 300-second/32-invocation planning continuation is a bounded example only. Verify installed native runtime enforcement separately from procedural call ceilings. Budget exhaustion preserves artifacts and stops; a new bounded continuation requires explicit Orchestrator correction under the user's authorized scope, never automatic looping or added deployment authority.

## Dependency and lifecycle rules

Create prerequisite/parent cards first, with initial blocking state, then children carrying dependencies at creation. Never create a runnable child then link later: dispatcher can race. Inspect installed `kanban_create` schema before use. Admission cards, human gates and implementation/review cards are distinct. Native approval completes the source, it does not message/reassign orchestrator. Use existing explicit downstream dependencies for substantive specialist stages and retain one outcome-owned Orchestrator assignment; do not add routing/read/review cards for each trivial probe. Arrange native durable resumption of the outcome owner rather than leaving an idle running worker or treating each routing result as success. Where supported, an active owner links a substantive specialist prerequisite to its own card and ends with native `kanban_block(kind=dependency)`: an incomplete parent puts it in `todo` for automatic promotion when that parent completes. Never make that specialist depend on the waiting owner, which would cycle. Verify injected schema/run ownership, edge and resulting state; no open parent means `needs_input`, not a usable wait loop. Confirm an actual resumed attempt before claiming runtime orchestration works. Never manufacture review metadata or a human actor. Stop after terminal native transitions.

## Evidence JSON and conservative invalidation

`identity` has absolute `repo`, `worktree`, `base_sha`, and lowercase SHA-256 strings `scope_digest`, `plan_digest`, `candidate_digest`, `policy_digest`. Hash actual canonical scope/plan/policy bytes. Candidate digest must cover HEAD/base identity, staged and unstaged binary diff, all owned untracked paths/content, deletions, modes and symlink targets; use a deterministic sorted manifest. Do not hash only HEAD or only staged files. Secret files are excluded from owned scope, never serialized into evidence. Record the exact digest command/manifest artifact.

Each bound evidence object contains an exact copy of `identity` as `binding`, plus a nonempty `evidence_ref` pointing to actual output/artifact or authorized human message. Evidence must be independently read, not trusted because JSON parses. v1 is deliberately conservative: all accumulated bindings must equal current identity, so changed candidate/plan/policy requires re-review and renewed/reconfirmed applicable approvals, not editing old binding values. Keep immutable old evidence and collect new evidence. This can over-gate harmless changes; it cannot silently grandfather them.

Required objects and fields are shown by synthetic `fixture()` in `scripts/test_validate_gate.py`; it is executable schema documentation, NOT production evidence. Fields:
- `risk`: low/medium/high; `browser_required`: boolean; `preflight`: PASS + repo + base_sha.
- `approvals`: plan/implement for non-low risk; deliver and cleanup always; each decision APPROVED, actor_kind human, actor, action, binding/evidence_ref.
- `reviews.plan` and `reviews.implementation`: APPROVED, native true, actual source_card, binding/evidence_ref by default. The sole non-native exception is the explicit [recovered plan artifact review](recovered-plan-review.md) schema; it requires actual independent ordinary-card approval, preserved timed-out provenance, verified idle, immutable matching plan hashes and user-authorized Orchestrator recovery. No implementation-review exception.
- `tests.tester`, conditional `tests.browser-tester`: PASS, integer exit_code 0, binding/evidence_ref.
- `docs`, `acceptance`, `wiki`: PASS, binding/evidence_ref. Wiki also authorized true and scope RW/task-summary.
- `delivery_policy`: allowed actions, repository, binding/evidence_ref; `requested_actions` must be nonempty subset. Include exact remote/ref/user decision in referenced policy artifact.
- `delivery`: PASS, delivered_sha, result_sha, binding/evidence_ref; `final_sha` must equal result_sha. Merge/squash may change delivered_sha; referenced delivery evidence must prove the mapping.
- `ci`: normally PASS, sha == final_sha, provider forgejo/github/other, evidence_ref, nonempty required_checks and checks [{name,status:PASS}]. No missing/skipped CI accepted.
- Explicit no-CI alternative: `ci.status=EXEMPT`, exact `binding`, nonempty `evidence_ref`, `sha=final_sha`, `target` equal to `delivery.target`, and both `checks=[]` and `required_checks=[]`. Also require `approvals["ci-exemption"]`: standard human APPROVED/action/binding/evidence_ref fields, `action="ci-exemption"`, `repository=identity.repo`, `target=delivery.target`, `scope="no-ci"`, `sha=final_sha`, and nonempty `policy_ref` to an EXISTING user policy. Independently read that policy and human decision: they must authorize this repository, target and no-CI scope; a bot assertion, unrelated general policy, or this installation request is not authorization. Reconfirm against changed candidate/scope/plan/policy/base/worktree or final SHA; never refresh old bindings by editing evidence. The validator checks structure, not authenticity or wall-clock revocation: caller must check current policy/decision and revoke stale evidence before each release. EXEMPT cannot override observed/required checks, bypass delivery/review/test/cleanup approval, or create no-CI policy. Synthetic examples live in `scripts/test_no_ci.py` only.
- CLI reports `status=EXEMPT` and `ci_status=EXEMPT` on admitted exempt close/cleanup, never CI PASS. Compatibility field `passed` means gate admitted, NOT CI ran/passed. Blocked evidence reports BLOCKED; earlier stages report CI NOT_EVALUATED.
- `beads`: exists boolean, if true actor/owner equal plus nonempty handoff evidence. Caller verifies this is actual current actor ownership.
- `cleanup`: dry_run/clean/integrated true, nonempty exact targets and approved_targets, also equal to approvals.cleanup.targets, binding/evidence_ref. References must include exact branch/ref SHAs and approval of that inventory.

Run validator on immutable evidence captured immediately before release. Exit 0 means supplied evidence is structurally consistent, not that it is truthful, authenticated, current on disk, or wired into Hermes. Do not use test fixture output to claim live pipeline execution.
