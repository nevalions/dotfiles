## Procedure
At Kubernetes or cross-repository application intake, load [Kubernetes routing and deployment maps](kubernetes-pipeline.md), then the application's evidence-labelled map (starter: [yt-downloader](deployment-map-yt-downloader.md)). Populate the [map template](../templates/deployment-map.md) before admission; unknown deployment triggers or authority block publishing, not local evidence preparation. Keep new application-specific maps and live image/UID bindings in maintained project documentation or durable task evidence, with source and freshness labels; link them from the assignment rather than adding one skill reference per incident. Keep reusable map fields and routing rules in this skill. These are maintained shared instructions, not an overlay or new production authority.

Load [the contract](contract.md) before dispatch or handoff. For repository candidate setup, also read [verified workspace lifecycle](workspace-lifecycle.md): bind all stages that edit or validate the same candidate to its owned native Git checkout using Kanban `dir`, not a removable `worktree`. Bind non-repository operational packets to a retained task-owned directory instead; coordination cards must explicitly identify each specialist's candidate rather than treating their own working directory as a shared repository. Missing CI remains blocked; explicit human-policy-bound no-CI records report EXEMPT, never CI PASS. Run `python scripts/validate_gate.py evidence.json STAGE` from this skill directory before downstream release; development stages are `plan`, `implement`, `deliver`, `close`, `cleanup`; independent research admission uses `research`. Nonzero exit blocks the action. Read the JSON errors, correct upstream evidence, then revalidate. Never edit evidence to manufacture permission. For Forgejo transport and CI evidence, follow [read-only CI verification](forgejo-verification.md); authentication, fixture validation and live candidate acceptance are separate checks.

This is an instruction-level workflow with a standalone deterministic evidence validator, NOT an installed Hermes core hook, authenticated approval service, security sandbox, or universal native `require_review` lock. The caller must collect truthful fresh evidence and enforce the result. Loop prevention here is an author/reviewer protocol using existing native block before a rejection can redispatch the author. Verify shared-skill consumer instructions and offline evaluator behavior; do not claim scheduler enforcement, install runtime hooks or require core patches/canaries. If a worker lacks block or owner-notification capability, retain evidence and request the exact supported parent action without request_changes or a bypass. Continue authorized application work independently of platform improvements. Report the exact enforced subset separately from advisory signals and unavailable telemetry; a review-cycle brake alone does not prove global token optimization or autonomous Orchestrator recovery. Native review approves/completes the source card; separate dependency cards carry downstream stages.

Use `python -m unittest discover -s scripts -p 'test_*.py' -v` for offline policy tests. Tests use synthetic evidence, never production boards, trackers, credentials or publishing. Models are unchanged. The validator never writes Git, Kanban, Beads, wiki or remotes.
