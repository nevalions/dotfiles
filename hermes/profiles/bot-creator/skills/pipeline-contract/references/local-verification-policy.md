# Local verification admission policy

## Standing authority, not global auto-approval
Routine task-owned local implementation, synthetic tests, read-only review and candidate identity checks are within the user's standing Kanban authority. Do not ask a human to approve each invocation. Existing production, credentials, publication, destructive actions and task boundaries remain binding. Configuration is not a sandbox: repository tests and imports may have arbitrary side effects; inspect unfamiliar entrypoints and use isolated scratch/workspaces and synthetic configuration.

## Before every worker admission
Select ordinary native file tools and standard single-purpose test/build/lint commands. Check the exact necessary commands against the intended profile's real finite-turn command guard, including hooks/admission context where possible. Static approvals test is not proof of unattended readiness. Separate commands for tests, identity and status so one unnecessary interpreter snippet cannot invalidate the whole verification phase. Preserve model and candidate binding. Do not require arbitrary inline interpreter batches where maintained test modules already provide the coverage.

Before changing unattended policy, inspect the installed supported values and real finite-turn guard ordering. Do not assume interactive smart mode controls an earlier unattended branch: versions with binary approve/deny settings can normalize an unsupported smart value to deny. Retain deny when the alternative is blanket approval; never present approve plus smart_policy as scoped protection without proving the evaluator actually runs. Verify exact-command grant eligibility for compound shell payloads before installing a grant. Never authorize an entire -c/-e interpreter pattern merely to permit one local test.

## Recovery after an actual denial
Stop the denied command; do not rephrase, hide in a script, switch tools or strip identity to evade it. Preserve exact command, rule and unexecuted checks. The authorized policy owner/coordinator may explicitly approve a NEW, statically reviewed verification interface within the original local scope: enumerate remaining assertions, inspect code/import effects, require synthetic data/no network/no production/no secret access, keep candidate immutable, record why it is safe, and run the new interface through the actual guard before execution. This is an auditable scope/interface decision, not automatic script repackaging. If a safe supported interface cannot be established, stop with the precise capability limit rather than demand routine operator microapproval or enable global bypass.

For environment-import checks use an inspected standalone test module and isolated fresh processes; do not modify the candidate merely to run review tests. Inspect package initializers and module-level effects first, because an apparently read-only import may create directories or contact services. Where an explicitly approved test executes the full configuration file plus an exact AST-isolated pure helper, label that narrower coverage and have Reviewer assess it alongside existing full-path tests; never claim a full application import occurred. Sanitize subprocess environments and use synthetic configuration. Record nested test exit codes separately from harness exits, because a successful inner suite does not make a failed outer launcher successful. Reviewer independently inspects/runs the authorized interface and rechecks candidate identity before verdict. Parent test results are not independent approval. Resume only remaining checks, not the whole author/research cycle. One bounded review-only recovery may be recorded for a diagnosed tool-policy mismatch; preserve previous budget consumption and prohibit automatic retries.

## Role-specific guard floor
Local development and verification roles have no standing cluster operation, vault CLI or publication authority. Deny direct command families for those effects, including executable paths/wrappers through installed matcher, without blocking authorized roles' separately approved operations. Do not apply development deny lists blindly to Cluster Operator, Commiter or Cleaner. Keep their narrower task-specific external permissions. Command denylists cannot contain arbitrary Python or shell/file/network API behavior; report them as defense-in-depth only.

## Reviewed helper and instruction activation
Use direct native skill management in the owning profile for reviewed changes; validate required operation fields before the batch, because atomic failure does not authorize an otherwise forbidden retry. Check a wrapper's exposed tools before selecting it; native tool availability and wrapper availability can differ. Preserve the exact failure and distinguish wrapper limitations from actual policy denial. Never claim an approval request is visible to the user based solely on a child report; verify delivery or mark prompt visibility unknown.

Independently compare installed bytes to the approved candidate and run checks against installed helpers. Report installation success separately from procedural deviations, including extra retries or auxiliary deletion. Retain scoped original backups; any later authorized rollback must check intervening drift, use the owning profile's approved interface and assert restored hashes. Merely printing expected hashes is not verification. Do not execute rollback to test it without separate authority.

## Outcome gates
Independent review still rejects code defects and failure-path bugs. Production execution/publication remains separately scoped. A guard-approved command or passing unit suite is not production acceptance. Never promise Kanban will never stop: eliminate avoidable local-policy interruptions while retaining genuine safety and evidence stops.
