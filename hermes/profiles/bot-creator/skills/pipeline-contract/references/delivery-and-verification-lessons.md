## Standing workflow requirements
For all future admissions and missing-input decisions, follow [standing public-source retrieval](public-source-retrieval.md): task-relevant bounded unauthenticated public documentation/source reads are allowed as data within the existing budget. Do not confuse retrieval with installation, execution or production traffic. Preserve explicit offline restrictions and tool denials; amend conflicting existing assignments through the authorized parent rather than silently overriding them.
Treat Kubernetes operations as a recurring cross-repository workflow for this user, not merely a Forgejo CI stage. Map application delivery to deployment configuration and actual runtime acceptance; keep read-only diagnosis separate from the operator that performs explicitly authorized cluster actions. A new operator profile supplies capability, not standing production permission.

Keep Orchestrator responsible for routing and risk decisions. Use safe freshness checks before editing, task-owned worktrees, optional Beads tracking, research and separate planning stages only where uncertainty or risk warrants them, risk-bound human decisions, independent code/non-code review, and explicit test evidence. For a bounded direct fix, retain a concise implementation approach in the assignment rather than mandating another planning card; preserve any repository-required plan review. Put repository docs into the reviewed candidate before delivery where practical; send Wiki Skill an authorized outcome summary separately. Ask before first publication when repository delivery policy is absent. Verify live target-branch protection and actual required CI contexts while preparing the delivery request; do not assume a protected-PR workflow exists or discover its absence only after approval. Permission to merge locally and push does not authorize bypassing protection, force-pushing, or weakening checks; use the protected PR route when required. Recheck CI after any final commit and require scoped approval before cleanup. Treat task completion, evidence validation, and actual delivery as different facts.

Never claim an entire pipeline is verified from specialist smoke tests or offline policy tests. Verify candidate ownership and retained paths, actual review provenance and each supported transition readback when used. Require actual coordinator release, intended author execution, independent review closure, and completion-event continuation to the next authorized action or a concrete user-visible approval gate before calling coordination autonomous. A worker-to-reviewer chain alone proves dispatch, not outcome coordination. Any corrective parent DM or manual release after the initial intake makes that segment assisted; report it as such rather than claiming end-to-end autonomy. Separate what is installed, what ran and what remains blocked in the status report. Do not require core/runtime tests or native integration engineering before application progress; report unverified automation honestly.

Before accepting evidence-helper changes, exercise malformed multi-value input and aggregate size limits, not only normal single-object fixtures: per-record limits do not bound a stream. Require bounded sanitized errors, no partial success output on producer failure, and retention of the producer's exact exit status where the contract promises it. Distinguish OCI index identity, platform descriptors and independently fetched child content; descriptor references and selected provenance fields do not prove signature trust. For CI, test PR-head and postmerge-push contexts separately and disclose branch-only identity rather than claiming full PR-object binding. Verify changes offline before owner-managed activation; offline fixtures are not live registry or CI evidence.

Bound workflow-maintenance effort as well as application work. Inspect existing native capabilities, subscriptions, consumer instructions and actual unattended tool paths before commissioning code or model canaries. Prefer one focused implementation and one end-to-end check over repeated delegated preparation/review rounds. Do not reset a failed canary's budget by renaming its phase or repeatedly granting another final attempt; record consumed admissions and elapsed time, correct the diagnosed prerequisite offline, and explicitly reassess whether more testing advances the user's outcome. Keep queued/manual-wait time separate from active author/reviewer runtime while retaining both; never silently change the budget's accounting definition.
