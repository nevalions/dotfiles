# Bump and deploy in kube-lvl47

This skill is a checklist, not authorization. Follow the current repository instructions, task admission rules, and operator-approved write scope. A local bump is not a request to publish or deploy. Work in an isolated task worktree from refreshed `origin/master`; retain unrelated changes.

1. **Find the actual source and targets.** Map every affected cluster, HelmRelease or image pin, values source, current documentation, and owning Flux Kustomization. Read `CLAUDE.md` (HelmReleases, Harbor, warmup refs), `docs/operations/parallel-work-gitops.md`, and any app runbook. Review upstream changes and keep historical notes intact. Image-only bumps may use `scripts/bump-image.sh`; review its scope and the auto-deploy policy first.
2. **Validate before shipping.** Render the old and new charts with each cluster's real values, release name and target namespace. Compare resource identities, CRD specs, image tags, storage and configuration changes; inspect expected rollout effects. Build affected Kustomize layers and run targeted lint, contract and parity checks. Update `registry-mirror/warmup-refs.yaml` in the same PR only where Vas image refs change, and verify those refs resolve via zot.
3. **Publish required artifacts before the GitOps merge.** If `sourceRef` is Harbor OCI, a new upstream chart tag is not automatically present in `oci://docker.butakov.su/library`. Fetch the upstream `.tgz` via the GitHub release-asset API, verify its published checksum and metadata, and push it when authorized. Pull it back from the exact configured source; verify the package checksum and record the OCI digest. If already present, verify it rather than overwriting it. Harbor's own chart is packaged differently; follow `CLAUDE.md` and prove packaging equivalence. Do not merge a pin Flux cannot fetch.
4. **Ship through Forgejo.** When authorized, commit only scoped files and use `scripts/ship.sh` from the task worktree. Use `--publish-only` if independently gating the merge; resume the same PR with guarded shipping after applicable checks pass on the exact ready head. Never merge into local `master`. Verify the server-side merge and all applicable CI on the exact merged SHA. Do not treat stale, skipped, or missing checks as passing.
5. **Verify live, read-only.** Prefer `cluster-operator` through the approved Hermes Observer. Routine observer RBAC covers Flux in `flux-system`, not monitoring workloads. The user kubeconfig is temporarily usable as a read-only verification fallback when the observer is unavailable or out of scope; confirm the current authorization and use explicit context, namespace, and a bounded request timeout. Never use the fallback for mutation. Verify the owning Flux Kustomization is Ready at the intended revision (or a verified descendant retaining the change), the HelmRelease's deployed chart and current Ready generation, and the actual workload readiness. Locate HelmRelease and workload namespaces separately. Normally the Forgejo webhook or Flux poll reconciles without manual intervention. If live reads fail, report the verification gap rather than declaring success.
6. **Report evidence.** Record source/package provenance, exact PR and merge SHAs, CI runs, per-cluster revision and workload health, and any fallback used. Close and sync only when all applicable gates pass and tracker writes are authorized. Do not put credentials or raw kubeconfigs in logs or notes.

Verified example: kube-lvl47 PR #711 (`kube-8afd`), chart `92.16.1` → `92.16.2`. See the local wiki topic `kube-lvl47-bump-and-deploy` for the audit trail.
