# Global Instructions for Pi

These are the Pi-specific defaults. For detailed user workflows, consult the relevant shared skill in `~/.agents/skills/` and, when needed, the corresponding section of `~/.codex/AGENTS.md`. Its Codex-only subagent, model-routing, hook, and approval instructions are not Pi capabilities. Do not claim delegation, model changes, or approval gates that the runtime does not provide.

## Scope and evidence

Make surgical changes and preserve unrelated work. Verify outcomes with targeted checks; distinguish evidence from assumptions and reassess after repeated failures. For new repository-changing tasks, use a task branch and isolated worktree; read-only work needs neither. Follow repository-specific setup and integration instructions.

## Git and CI

Use the shared `commit-task`, `merge`, and `pr` skills for their matching workflows. Commit-only never authorizes pushing or merging. An unqualified push means validate, squash-merge into the actual default branch, and push the result, unless repository policy says otherwise. Explicit branch-only pushes and PRs keep the task branch. For `kube-lvl47`, use a task worktree and the server-side PR flow through `scripts/ship.sh`; never merge into local master.

Stage explicit files only; use non-interactive Git, a message file for multi-line commits, and no co-author lines. Do not tag, release, or change settings without authorization. Verify required CI for the exact PR head or merged commit as appropriate; do not remove branches or worktrees until the authorized merge and required CI are verified. Missing evidence is not a pass.

## Tasks, memory, and credentials

- **Beads:** Use for durable task state and dependencies; ask before creating or updating an issue unless already authorized. Follow the repository's documented sync policy. If delivery scope or repo standing policy covers sync, perform it and verify remote publication without asking again. If unrelated pending changes would be included outside scope, preserve them and report the blocker. A local tracker mutation or Git push does not prove tracker publication.
- **Pre-plan knowledge pass:** Before substantive planning or implementation (including any planner handoff), the top-level session (plain Pi or the `pi-team` coordinator) performs one read-only pass combining existing scoped Honcho recall and a bounded, relevant `wiki-skill` lookup. Check recalled and wiki claims against current repository or primary sources; missing or unavailable context is nonblocking. Pass only sourced facts and explicit caveats in child handoffs so children do not duplicate lookups, and never pass Honcho grants, tokens, or raw data/transcripts to a child.
- **Honcho recall:** In the pre-plan pass, base Pi or the team coordinator runs `python3 -I ~/.pi/agent/honcho-cli/recall-scopes.py` from the task checkout. If it returns targets, query `honcho_recall` in `hermes-personal` with observer `pi-coordinator` and the first target for relevant prior decisions. Query a returned `project-*` target for cross-repo topics and `code-wide` only for broadly applicable research. Use short, non-sensitive queries, not raw prompts, credentials or logs. An empty list means no automatic lookup. Respect opt-outs, reuse session results and verify recalled claims; if memory is unavailable, continue. Workers and planners use the coordinator’s sourced handoff rather than repeating recall. Query `linroot` only for user preferences. These local routes authorize lookup only; they do not provision peers or expand any write grant.
- **Honcho drafts:** Planner and reviewer may return a concise draft in their task handoff, labeled with the task ID, source/candidate, evidence and uncertainty. Drafts are not Honcho memory. Scout, worker, planner and reviewer never publish.
- **Honcho publishing:** Only the top-level operator-authorized CLI session (plain Pi or the coordinator in `pi-team`) may append via `honcho_publish`, and only to the exact workspace, observer peer, target peer, session and task in its launch grant. When a publisher is present, inspect its scope and run publication during shared closeout without a reminder. Publish repository-specific facts only to the matching repository peer. A granted `project-*` target is only for verified cross-repository findings for its member repositories; `code-wide` is only for broadly reusable verified research. Never widen the audience to fit an available grant. Use a matching repository peer for verified durable repo facts; use `linroot` only for an explicitly confirmed durable user preference the user authorized saving. Do not publish to other people or unrelated projects. Follow `honcho-save` and readback boundaries: cite an immutable candidate or primary source, checks and their results, and independent verification (including review when required). A draft, inference, or missing or stale check is not evidence. Read back the exact conclusion before claiming success. No raw transcripts, personal data beyond approved preferences, sensitive evidence, or credentials. If there is no eligible verified fact, no exact matching grant, or a write is denied, perform no write, leave a useful draft if appropriate, and continue without bypassing the gateway. No deletes, edits of existing memory, provisioning, or administrative operations through Pi.
- **LLM wiki:** For prior research, decisions, or documented procedures, use `wiki-skill` at `/home/linroot/vault/linroot-wiki-code`. Read `AGENTS.md`, `SCHEMA.md`, and `RW/index.md` before opening relevant pages, keeping pre-plan lookups bounded and read-only. Wiki writes are separately authorized; review, lint, and Git rules remain in force (authorized wiki edits include lint, commit, push, and verification on the configured remote by default unless an explicit draft, local-only, or no-push request overrides this; never write to `RO/`). Auto-publish is disabled: absent explicit authorization, leave only a useful draft; any future automation requires both an explicit allowlist and standing ingest authorization.
- **Shared closeout:** In both plain Pi and `pi-team`, shared closeout belongs to the top-level session before the final report and runs without repeated requests only after the last authorized gate in scope is verified (local checks alone for local-only work, and commit only when authorized/in scope, exact pushed or PR SHA checks if required, exact integrated SHA checks if required, and verified serving rollout if in scope). Never run Honcho or wiki publication merely on a CI notification, failure, shutdown, or timeout. Pre-plan lookup and shared closeout grant no new Git, deployment, or tracker authority.

At closeout, report Git delivery, Beads sync, wiki publication, and Honcho publication separately when relevant. Mark local-only, pending, blocked, and verified remote outcomes explicitly.

Do not store credentials in any memory system.

Keep secrets out of terminal output, transcripts, chat, and tracked files. Prefer existing authenticated access; on this machine use `rbw` when a vault lookup is needed and pass secrets directly to the consuming process. Do not assume Codex MCP approval rules exist in Pi: use tools only within the user's authorized scope.

Prefer official documentation and standards for research. Use the shared `scan-security` skill when reviewing security and do not file findings or make unrelated fixes without authorization.
